# Matched Source Workflow

`scripts/build-matched-objects.ps1` is the general build lane for maintained
source that should be compared against the Ghidra target disassembly. It uses
the same ARM flags as the runtime seed, but reads its source list from
`metadata/matched_sources.txt`.

```powershell
.\scripts\build-matched-objects.ps1
```

To force a specific ARM GNU toolchain, pass its install root:

```powershell
.\scripts\build-matched-objects.ps1 -ToolRoot C:\Users\xander\Downloads\arm-gnu-toolchain-15.2.rel1-mingw-w64-x86_64-arm-none-eabi
```

Outputs go under ignored `build/matched/`:

- `*.o`: compiled object files.
- `*.dump`: objdump output.
- `manifest.json`: compiler, flags, and source list.
- `compare_matched_objects.{json,md}`: normalized instruction comparison
  against `ghidra_export/disassembly.txt`.

The comparator intentionally normalizes equivalent ARM spellings before
classifying matches. Examples include stack transfer aliases, shift aliases
such as `lsls` versus `movs ..., lsl`, and conditional memory-transfer suffix
ordering used by Ghidra versus GNU objdump. Keep new normalizations in
`scripts/compare_runtime_objects.py` or the relevant generator before treating
a near miss as a real codegen mismatch.

After rebuilding the matched lane and any structured units, generate the
commit-facing metric snapshot:

```powershell
python .\scripts\report_porting_metrics.py
```

This writes `analysis/porting_metrics.{json,md}` and prints the numbers that
must be reported with each porting commit: exact matched functions, exact
matched files, structured source files that compile, and structured functions
that are still non-exact.

The lane intentionally allows unresolved symbols because matching work is done
at object level. Add one source file or small source group at a time, then use
the comparison report to decide whether a function is exact, close, or still a
semantic-only reconstruction.

The main reconstruction source is the N64 decompilation wherever OOT3D keeps
the same gameplay logic. Track those relationships in `metadata/n64_port_map.csv`
and regenerate mapped N64 extracts with:

```powershell
python .\scripts\extract_n64_port_units.py
```

This writes grouped packets under `analysis/n64_port_units/`. Treat those
extracts as the first draft for structured OOT3D source, then adapt offsets,
helper names, callee prototypes, data symbols, and split states until the
compiled ARM object matches.

For new imports, start from `analysis/n64_importability.md`, not from raw rank
score alone. Rows classified as `direct-import-test` are the candidates to try
as matched C first. Rows classified as `split-or-subsystem` should feed shared
types, offsets, and helper-role reconstruction before any exact-source attempt.

To bootstrap a new source file from an already identified target function, use
the naked seed generator:

```powershell
python .\scripts\generate_naked_match_seed.py `
  --name oot3d_boss_va_zapper_hold `
  --signature "void oot3d_boss_va_zapper_hold(void* bossVa, void* play)" `
  --out build\scratch\z_boss_va_hold_seed.c
```

That output is a starting point for object comparison, not the final
decompilation style. Replace naked transcriptions with structured C as the
surrounding types, globals, and callees become reliable enough to keep the same
object match.

The first non-runtime unit is `src/overlays/actors/ovl_Boss_Va/z_boss_va.c`.
It keeps default exact anchors for the matched lane, while
`OOT3D_BOSS_VA_STRUCTURED_PORT` builds N64-derived structured ports for the
7-function zapper state batch currently under reconstruction. Track its
object-match status in `analysis/structured_port_status/boss_va_zapper.md` and
the global unit index in `analysis/structured_port_status/index.md`,
regenerated by:

```powershell
.\scripts\refresh-structured-port-units.ps1
```

Add new batch units to `metadata/structured_port_units.csv`. The refresh helper
extracts all mapped N64 source, rebuilds the default exact lane, builds each
structured unit, and regenerates per-unit plus global status reports. Use
`-Unit` or `-PortFile` to refresh a subset while iterating on a single source
lane.

Structured units are allowed to be non-exact while they are being reshaped:
they stay outside `metadata/matched_sources.txt`, compile in their own output
directories, and are summarized by `analysis/structured_port_status/index.md`.
This keeps the default maintained lane exact while still converting reviewed
N64-derived batches into measurable C.

For a promotion-oriented batch view, run the structured C match gate:

```powershell
python .\scripts\structured_c_match_gate.py
```

This rebuilds every `metadata/structured_port_units.csv` lane with the OOT3D
ARM compiler, compares all mapped functions, and writes
`analysis/structured_c_match_gate.{json,csv,md}`. Only rows classified as
`exact-c` are eligible to replace an exact seed in the maintained baseline.
Rows classified as `codegen-near` are the next fastest C-matching targets,
because the semantics are already close and the remaining work is usually
source shape, prototype, type, or compiler-profile pressure.

When a structured function only matches under a non-default compiler profile,
keep the global build at `-O2` and apply the narrower profile locally with a
function attribute after proving it through `search_structured_compile_profiles.py`.
The `message_start` lane is the first promoted example: `Message_StartTextbox`
matches as C under a local `optimize("O1")` profile while the maintained build
continues to run through `build-matched-objects.ps1`.

For public structural inline seed batches, use
`scripts/generate_public_structural_inline_matches.py`. The default category is
`structural-near`; pass `--exclude-baseline-exact` when feeding it an audit CSV
that marks already matched rows so the generated seed file stays focused on
unmatched candidates.

The leaf pseudocode lane is similarly mechanical:

```powershell
python .\scripts\probe_leaf_pseudocode_c.py --promote-exact
```

If the current `analysis/leaf_function_candidates.json` points at decompiled
files that no longer exist after a Ghidra export or rename pass, the probe now
marks those rows as `missing-source` and continues. Refresh the leaf candidate
rank before expecting new promotions; a zero-exact run intentionally leaves
`src/leaf_pseudocode_matches.c` unchanged.

Rows in the leaf `codegen-near` queue can be promoted manually when a small
plain-C source-shape rewrite proves exact under the default matched build. Keep
those hand-shaped promotions in `src/leaf_codegen_near_matches.c`, document the
reason in `analysis/leaf_codegen_near_manual.md`, and leave
`src/leaf_pseudocode_matches.c` under the ownership of
`probe_leaf_pseudocode_c.py --promote-exact`.

Local GCC `optimize(...)` attributes are acceptable in this manual leaf lane
only after a scratch probe proves the exact profile and the full matched build
still reports every maintained function as exact.
Minimal inline asm is acceptable only as an explicitly documented interim entry
when the remaining mismatch is a compiler lowering choice that cannot be made
object-exact with C source shape alone.

Use `scripts/probe_leaf_codegen_near_profiles.py` to make that profile search
repeatable. It reads the leaf probe report, skips functions that are already
exact in the maintained baseline by default, and writes
`analysis/leaf_codegen_near_profile_probe.{json,csv,md}`. Treat
`exact-profile` rows as candidates for a reviewed manual source-shape promotion,
not as automatic decompilation output.
