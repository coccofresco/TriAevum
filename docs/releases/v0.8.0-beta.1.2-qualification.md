# Beta.1.2 Release Qualification

Date: 2026-10-22. Scope: Windows x64 portable ZIP, Linux x86-64 AppImage and
Linux x86-64 Flatpak bundle (candidate b12). Supported inputs: decrypted EUR
and USA dumps, original and Rev 1, as for [beta.1](v0.8.0-beta.1-qualification.md).

## Source and Package Boundaries

- Runtime/source freeze: `1c07ff0c99a1d8ad60ec7d7e78be5879c588bc3d`
  (branch `release/0.8.0-beta.1.2`). The packages are built at `50a399d`,
  which changes only the release tooling (corpus gate 1 below, its tests and
  the preparation document); the later commits add the release records
  (release notes and this file). No runtime, Forge or shader source changed
  after the freeze.
- The first candidate (frozen at `13a95dc`) was refused by the release audit:
  `TriAevum.exe` imported `vkGetPhysicalDeviceMemoryProperties2`, the Vulkan
  1.1 query behind the #98 VRAM budget, from `vulkan-1.dll`. A loader older
  than 1.1 would not have started the process (the beta.1 `0xC0000139`
  reports, issues 12 and 35). `1c07ff0` takes the command from the instance at
  run time like the other 1.1 queries; without it the budget queries report
  nothing and only the budget-based texture release and grass refusal are
  withdrawn. Both executables pass the import audit (Vulkan 1.0 and WSI
  commands only); a developer run still reports the budget (11,340 MiB on the
  Windows machine). The three files the fix touched are outside the corpus's
  decision-policy set (below), so the recordings made at `13a95dc` stay
  qualified and the corpus was regenerated offline at `1c07ff0` from them.
- 59 commits since beta.1.1 (`17218b0`), grouped and checked as the change
  matrix below. The developer build of the freeze is complete again under
  clang 22 (`d8df14f`: gmock flag, cross-title boundary of the shared motion
  provenance header); the TopScreen asset tools import from the distribution
  root (`a4b881d`).
- All packages pass the allowlist/hash/source audit with no errors. Windows
  contains 93 catalogued files (the root holds only Forge, the license and the
  README; the runtime lives under `runtime/`, notices and the manifest under
  `docs/`); Linux contains 541. The AppImage and the Flatpak carry the same
  audited Linux inventory.
- Precompiled title module: rebuilt from scratch at the freeze with the
  beta.1.1 profile-guided data (`title.profdata`, SHA-256 `431da79d…`, shipped
  inside every package's translated title source archive) and byte-identical
  to beta.1.1: Windows `91f18fc498fa8a3a…` (same translator identity, toolchain
  and program), Linux `122d99685e9ba013…`. DLSS and MXAO modules unchanged
  (Windows `8ec337a5…` / `ee7f04b6…`, Linux `84dcc345…` / `64b10155…`).
- New package content: the SingleScreen HD font (`ltn16`, bundled with the
  author's consent, see `LICENSES/`), and the Forge download of the HD UI
  texture pack by language (downloaded only with the user's consent, never
  packaged). The Vanilla+ Link remodel is a local RomFS overlay the user
  provides; nothing of it is distributed.
- Runtime and Forge are packaged separately from ROM-derived data. No ROM,
  `code.bin`, save, capture or SDK is distributed.
- AppImage packaging tools re-pinned to the tagged releases appimagetool 1.9.1
  and type2-runtime 20251108 (SHA-256 in `scripts/package-appimage.sh`); the
  earlier `continuous` assets were replaced upstream.

## Enhanced Shader Corpus

The corpus is regenerated from recorded variant requests, not from shader text
(issue #76), and qualified by three release gates. Everything was recorded
again at the frozen runtime: the beta.1.1 recordings are not reused.

- Gate 1 in this release keeps, of each recording runtime, the decision-policy
  subset of its build inputs (the files the generator shares with the runtime
  and the modules that compose a draw's variant request: 469 of the 1,466
  Windows files, listed by `shader_corpus_qualification.py policy-inputs`).
  The loader fix is outside that set, so the recordings below stay valid for
  the release runtime and the regeneration ran offline.
- Recording at `13a95dc` (equal to the release runtime in every
  decision-policy input), split across two machines
  under the product and the maintainer's graphics profiles (both regenerated
  from the frozen build): the Better-scene sweep on Windows for scenes 0-11
  (120 visits; the 20 failures are the adult Castle Town Entrance, Market and
  Hyrule Castle warps, which fail in every sweep) and on the Linux AMD
  reference machine (developer build of the same commit) for scenes 12-48
  (102 visits, 0 failures); then event sessions on Windows (Barinade under both
  profiles, Kokiri storms under both, a game over, a cutscene) and the boot to
  the file select under both. Both halves' runtime inputs match the release
  checkout byte for byte (three working-tree files were normalized to LF for
  that).
- Canonical programs: the two Citra transferable caches as before, and the
  capture corpus through the import the 2026-10-19 regeneration wrote from it
  (`--capture-inventory`, new in this release's tooling): the captures
  themselves were no longer at hand, the importer binary is unchanged since
  2026-10-17 and depends only on the captures, and the regeneration record
  carries the SHA-256 of the reused import and of the importer. The
  surviving capture corpora on disk reproduce 501 of its 513 programs; the
  12 others come from scene-setup variants captured in September.
- Regeneration (offline, at `1c07ff0`, from the `13a95dc` recordings; a
  first regeneration at `13a95dc` produced the same pack): 10 sessions,
  45,684 requests, 0 witness mismatches, 0 uber gaps, 0 resolve failures;
  synthesis of the five product sessions over the caches: 468 programs, 30
  contexts, 28,080 resolves, 6,218 new modules. 7,566 modules (770 MB, all
  from the SPIR-V compile cache, 0 compiled), pack SHA-256
  `5c69ef5aa5e7aec3a3413d559f03bb0c8f3442735d482a6370f2858ed51cdc36`, 1,317
  runtime pipeline recipes plus the 521 capture pipelines; closure 0 missing
  modules, 0 missing recipe modules (gate 2). Same module count as the
  2026-10-19 regeneration; the recipe set grew by 29.
- Gate 1 (freshness): `qualified` against the release checkout, generator
  (264 files) and per-session decision-policy inputs (469 files, the same
  set and digest for the Windows sessions and the Linux half): 0 changed, 0
  missing.
- Gate 3 (developer launch at `13a95dc`, with this same pack, empty renderer
  cache, no recorders): Barinade
  fight, Kokiri storms and boot to the file select, each under both profiles,
  game over and cutscene (8 runs): 0 shaderc calls, 0 PICA pack misses, 0
  pass-artifact misses, 0 SPIR-V cache compiles, exit 0. The Linux half of the

## Known Limits

- Windows AMD drivers (amdvlk, Adrenalin) remain untested; the Linux RADV
  qualification above does not cover them.
- Intel Arc on Mesa anv (#72): unchanged since beta.1.1.
- #85 ("Cannot query the playable runtime"): unchanged; Forge records the
  runtime's output for the report.
- Pipeline recipes depend on when the runtime adopts an Enhanced pipeline, so a
  recording can miss a few; a missing recipe means the pipeline is created in
  game, never a shader compile.
- Linux without a connected display (Wayland session with no output): the
  runtime reports the SDL video failure and then crashes instead of exiting
  cleanly. Found during this qualification, when the reference machine's
  monitor was unplugged; not a package fault. Fixed in the runtime after the
  release (window teardown after a failed video init); the published
  packages still carry the crash, which only follows the already fatal error.
- Otherwise as beta.1.1.
