# OOT3D source-native host ABI audit

## Scope

This report records the systemic investigation performed before resuming boot
attempts. The audited surface contains 1,069 LLVM modules from the pinned
source-native snapshot around decomp revisions `2554aabd` and `fd4f1dca`.
The two revisions differ only in the startup callback pointer correction; the
global counts below are not affected by that local change.

The authoritative machine-readable report is generated by
`Oot3dHostAbiAudit` and currently lives at:

`build-source-native/abi-audit-2554aabd/host_abi_audit_v2.json`

## Why boot stopped

The canonical source retains the 32-bit ARM target ABI while executing as x64
host code. A recovered `u32` can therefore be either a guest address or a
pointer carrier whose pointee was allocated by a C function. The latter is
valid on ARM32 but loses the high half of an ordinary x64 stack pointer.

The notification startup crash was the first observed instance, not the root
problem. The whole-surface audit found:

- 10,138 function definitions and 67,702 direct calls;
- 2,147 indirect calls;
- 1,635 direct sites where an x64 stack pointer reaches an `i32` definition;
- 487 reconstructed stack pointers after width loss;
- 89 narrowed stack pointers passed through indirect calls;
- 15 direct host-global pointers passed to `i32` definitions;
- 6 additional host-address width-loss flows;
- 38,133 defined non-target globals, of which 644 are mutable;
- 6,990,517 bytes of non-target global storage.

Fixing callback signatures one at a time cannot close this class of failure.

## Stack evidence

The same audit measured every LLVM `alloca`:

- 4,970 static allocations;
- zero dynamic allocations;
- one function above 4 KiB;
- maximum static frame: 5,200 bytes;
- zero functions above 64 KiB.

A Windows x64 probe then executed a 6,144-byte frame on dedicated stacks below
2 GiB on both the primary and a worker thread. A pointer narrowed to 32 bits
and reconstructed retained the exact address.

The first large-frame probe failed because the MSVC `__chkstk` implementation
reads `NT_TIB.StackLimit` from `gs:[0x10]`. It tried to probe from the original
high Windows stack to the alternate low stack. Updating `StackBase` and
`StackLimit` for the duration of the stack switch made the normal, unmodified
`__chkstk` path pass. Disabling stack probes is therefore unnecessary.

## Rejected process layouts

### Entire executable below 2 GiB

A fixed low executable also caused Windows to allocate the initial stack and
heap in the low address range. Those allocations overlap the required guest
mapping at `0x00100000-0x005c8000`. Marking the executable non-LAA additionally
moved system DLLs into that range. This layout is invalid.

### Fixed low source DLL

A high host executable was able to reserve the exact guest regions, but
`LoadLibrary` did not complete when loading a fixed source DLL at
`0x50000000`. The behavior reproduced with only a two-function probe DLL and
no game code. This path adds loader dependence without solving the semantic
difference between guest function addresses and host function pointers, so it
is rejected.

## Selected architecture

1. Keep the host executable, runtime libraries and renderer at their normal
   x64 addresses.
2. Keep the exact direct-mapped guest regions unchanged.
3. Execute every canonical source entry on a dedicated stack below 2 GiB.
4. Temporarily publish that stack through `NT_TIB.StackBase/StackLimit`, then
   restore the original values before returning to host code.
5. Bind both `ScopedSourceAddressSpace` and `ScopedCtrHostServices` on every
   source worker thread before entering canonical code.
6. Convert target thread exit into a controlled return through the stack
   trampoline so the low allocation is released and the thread object is
   signaled.
7. Keep host-global/function address crossings as a separate audit failure.
   They must be normalized from a generated whole-surface ABI manifest or
   corrected by typed source evidence; they must not be hidden by PE layout.

The low-stack rule is a compatibility implementation of the recovered ARM32
ABI, not an A32 interpreter and not a gameplay fallback.

## Validation gates

Before a game run:

1. Runtime tests must pass for primary and worker low stacks.
2. A frame larger than the audited maximum must pass through normal
   `__chkstk`.
3. Local pointer narrow/reconstruct must be exact.
4. Exceptions must be caught before crossing the assembly boundary.
5. target `ExitThread` must return through the trampoline.
6. The ABI report must remain reproducible and retain all host-address
   findings even when ordinary details are truncated.

After those gates, perform one incremental build and one boot run with a
15-second watchdog. A new failure must be classified against the audit before
any code change; repeated per-symbol signature patches are not an accepted
workflow.

## Current whole-AOT contract

The current 1,075-source pipeline closes the scalar target-word class before
LLVM compilation. `lower_target_word_globals.py` emits a versioned
`lowered_snapshot_manifest.json`; `build_llvm_legalized_surface.py` rejects a
source root without that manifest, a stale lowering contract, a revision
mismatch, or an incomplete source set. Building whole-AOT directly from a raw
decomp snapshot is therefore no longer a supported or silent path.

The `target-word-lowering-v5-manifested-abi` snapshot applies 105,977 guest ABI
identifier replacements and 1,221 precise pointer declaration replacements.
The legalized-surface audit still reports 57 host-width accesses across 23
sources: 34 guest pointer loads, seven guest pointer stores, and 16
mixed-destination pointer loads. These are nested pointer fields and form the
next bounded ABI family; they are not scalar target-word literals and must not
be hidden by widening or permissive address resolution.

The build cache fingerprints transitive source dependencies and the lowering
contract. A no-change whole-AOT check is a fast path; the latest synchronized
tranche rebuilt 30 of 1,075 objects and updated only those archive members.
